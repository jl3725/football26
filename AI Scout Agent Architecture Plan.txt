AI Scout Agent Architecture Plan
Context
The football26 project is actively being refactored from a monolithic Streamlit dashboard + ETL scripts into a modular, agent-targetable "AI Scout" system for player/team analysis, role classification, similarity search, gap analysis, and transfer recommendations.
Recent work split app.py (~4600 lines) into src/ui/ modules (explicit goal: "split so agents can target specific tabs clearly").
Current "AI" is rule-based (percentiles, weighted cosine, trait mapping) with labels like "Vector RAG" (sklearn only).
DESIGN.md (the north star) describes a full hybrid Graph RAG + Vector RAG:
Vector: player stats embeddings for "similar players".
Graph: relations (plays_for, transferred, managed_by, teammate_of) in Neo4j.
LLM Orchestrator (LangGraph suggested) for routing + synthesis.
Current scope: EPL 25/26 only. Hardcoded sources, fixed 20-team dicts.
Scheduled "agents" exist but are external (Task Scheduler PS1 scripts + GH Actions for fetch_transfermarkt_injuries, sync_manager_profiles, fetch_news_daily).
Gaps: No real Vector DB / Graph DB / LangGraph / LLM orchestration yet. Many cross-cutting concerns still live in app.py (data prep, routing, Schedule/Player DB tabs not yet extracted).
Future: League expansion, full RAG, multi-agent scouting (beyond the current Streamlit surface).
The user needs a concrete plan for how many agents should emerge, what they should be, and how to structure the agentization to support the AI Scout vision while enabling league expansion + Vector/Graph DB integration.
Recommended Approach
Decompose into 11 specialized agents grouped into 4 layers. This provides clear ownership, testability, and incremental rollout without over-fragmentation. Use the existing pure functions as "skills/tools" that agents call.

Layered Structure (total 11 agents):
Data Layer (5 agents) — Independent ingestion/monitoring. Make league-agnostic (config-driven sources). Feed Vector + Graph DBs.
Players Stats Ingestion Agent (FBref + Understat + Sofascore enrichment).
Transfers & Roster Lifecycle Agent.
Injury Monitor Agent (already "agent"-named; add change detection + alerts).
Match / Lineups / Formations Agent (multi-source: FL, ESPN, API-Football).
News & External Signals Ingestion Agent (daily batch + DB updates).
Analysis Layer (3 agents) — Compute derived signals used by scouts.
Role & Archetype Classifier Agent (assign_role + badges + fine_group).
Similarity / Vector Scout Agent (build_embeddings + find_similar; evolves to real vector DB).
Team Metrics & Context Agent (build_team_unit_metrics + comp_context + schedule load).
Scout Layer (2 agents) — Core "AI Scout" output.
Tactical / Gap Analyst Agent (analytics factor lab, weaknesses, leader/gap extraction, injury impact, context briefs).
Transfer / Recruitment Scout Agent (recommend_signings + style vector fit + signing cards).
Orchestration & RAG Layer (1 agent) — The brain.
Scout Orchestrator Agent (LangGraph-based): query routing (Vector vs Graph vs Hybrid), calls specialist agents, Vector DB retrieval, Graph traversal (Text2Cypher or equivalent), synthesis + natural language explanations. Supports league expansion via config.
Why this number and grouping?
Aligns with current modularity (src/ui/analytics.py already documents itself as "evidence layer for the transfer agent").
Matches DESIGN.md phases and components (Vector for similarity, Graph for relations, LLM router).
Reuses existing code heavily (see below) instead of rewriting.
Supports expansion: Data agents become per-league or multi-league configurable; Orchestrator handles cross-league queries.
Avoids too few (monolith) or too many (micro-agents that are hard to orchestrate). 11 is manageable for one project.
Streamlit (app.py + src/ui) remains one consumer/view; agents expose structured data + HTML snippets for reports, CLI, future API, or other UIs.
Incremental: Start by wrapping existing functions; later replace sklearn with real embeddings/Vector DB and add Neo4j client to Graph-aware agents.
Trade-offs considered:
Monolithic "Scout Agent" (too coarse) vs 20+ tiny agents (high overhead).
Full LangGraph from day 1 vs start with simple router + evolve.
Per-league agents now vs single agents with league param (prefer latter for simplicity).
UI ownership: Keep rendering in src/ui; agents focus on logic + data.
Integration with DBs & Expansion
Data Layer agents write to shared raw DB + populate:
Vector DB (pgvector or Qdrant): player stat embeddings + text reports.
Graph DB (Neo4j): nodes (Player, Team, Manager, League) + edges from transfers/lineups/contracts.
Add LeagueConfig / source registry so agents work for EPL + future leagues (e.g., Bundesliga, LaLiga).
Orchestrator becomes the entrypoint for "AI Scout" queries: "Find similar players for my 4-3-3 in new league with budget X".

Verification Section (End-to-End Testing)
No-regression baseline:
streamlit run app.py on port 8501 still works fully (all 8 NAV tabs render identical output using the same functions).
Existing data pipelines still produce identical CSVs when run manually (python src/fetch_*.py, python src/build_team_unit_metrics.py, etc.).
Agent isolation & targeting:
Each agent can be imported and called standalone: e.g., from src.agents.analysis import RoleClassifierAgent; agent = RoleClassifierAgent(); roles = agent.run(team_df, pct).
UI modules remain importable by agents (test from src.ui.analytics import ... inside a mock agent).
Agent count & structure validation:
Run a smoke orchestrator query that routes to ≥3 different agents and composes results (e.g., "Analyze Arsenal gaps and recommend similar players").
Verify 11 agents (or grouped equivalent) exist with clear boundaries (no cross-layer direct calls except through orchestrator).
League expansion prep:
Add a second league config (e.g., mock Bundesliga) and show at least one Data Agent + Orchestrator handling it without hardcodes.
Metrics/roles/similarity remain comparable or configurable.
DB integration path:
Demonstrate (in test or script) a Data Agent writing player embeddings to a local Vector store stub and relations to a graph stub.
Orchestrator example using both (even if mocks initially).
Full flow:
End-to-end: User query (or test) → Orchestrator → Vector retrieval + Graph path + 2 specialist agents → synthesized scout report (text + HTML from existing UI renderers).
Scheduled agents still run independently and feed the stores.
Metrics:

Integration test in CI that exercises the modular imports + one full agent chain.
Confirm Streamlit uses agents for at least Analytics/Transfers/Player tabs (optional first step; can be gradual).
